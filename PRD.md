# PRD — Платформа санкционного мониторинга (API + Telegram Bot)

**Версия документа:** 1.0  
**Статус:** Draft for implementation  
**Целевая модель запуска:** один разработчик, VPS, поэтапное развитие

---

## 1. Обзор продукта

Платформа предназначена для:
- агрегации санкционных данных из множества внешних источников;
- нормализации и хранения этих данных в единой структуре;
- быстрого API-поиска по физическим и юридическим лицам;
- уведомлений в Telegram о загрузках, ошибках и операционных событиях.

### 1.1 Цель
Создать компактную, надежную и расширяемую систему, которую можно развивать итеративно одним разработчиком, добавляя новые источники данных и функциональность независимыми циклами разработки.

### 1.2 Ключевые продуктовые принципы
1. **API-first**: основной продукт — API, без обязательного публичного web-интерфейса.
2. **Bot-first operations**: Telegram-бот как интерфейс мониторинга и оперативных команд.
3. **Плагинная ingestion-модель**: каждый новый источник добавляется как отдельный модуль по унифицированному контракту.
4. **Безопасность по умолчанию**: HTTPS, изоляция БД, секреты вне кода, минимальные привилегии.
5. **Эволюционность**: архитектура допускает переход к микросервисам без переписывания доменной модели.

### 1.3 Non-goals (первый этап)
- Публичный пользовательский веб-интерфейс.
- «Тяжелая» микросервисная инфраструктура с первого дня.
- Полноценный ML matching в релизе 1.

## 2. Целевая аудитория и сценарии использования

## 2.1 Целевая аудитория
- Комплаенс-специалисты и операционные команды.
- Продукты/сервисы, которым нужна встраиваемая санкционная проверка через API.
- Владелец системы (оператор), который управляет загрузками и контролирует стабильность через Telegram.

## 2.2 Основные сценарии
1. **Поиск по имени/названию** через API с настраиваемой точностью.
2. **Проверка принадлежности к санкционным программам** и просмотр причин совпадения.
3. **Запуск и мониторинг загрузок** данных из Telegram.
4. **Получение тревожных уведомлений** о падениях ETL/API и аномалиях обновлений.

## 3. Область функциональности

## 3.1 Блок A — Источники и загрузка данных

### A1. Унифицированный интерфейс источников (обязательно)
Каждый источник подключается как отдельный модуль (plugin/adapter), реализующий единый контракт.

**Контракт модуля источника (концептуально):**
- `fetch(config) -> RawSnapshot`
- `parse(snapshot) -> list[RawEntity]`
- `normalize(raw_entities) -> list[NormalizedEntity]`
- `get_fingerprint(snapshot) -> str`

**Требования:**
- Источник добавляется независимо от других источников.
- Ошибка в одном источнике не останавливает обработку остальных.
- Источник можно включать/выключать конфигурационно.

**Acceptance criteria:**
- Новый источник добавляется отдельным pull request без изменения ядра системы.
- Для каждого источника есть контрактные тесты и минимальный набор фикстур.

### A2. Реестр источников
Система хранит метаданные источников:
- код источника;
- тип (xml/csv/json/api/html);
- endpoint;
- расписание;
- статус активности;
- правила ретраев;
- лимиты таймаута.

**Acceptance criteria:**
- Источники управляются через конфигурацию/БД без пересборки приложения.
- Возможен ручной и плановый запуск источника.

### A3. ETL orchestration
- Периодические и ручные запуски.
- Идемпотентность на уровне fingerprint версии.
- Retry policy с backoff.
- Логирование этапов и метрик выполнения.

**Acceptance criteria:**
- Повторный запуск с тем же fingerprint не создает дубли.
- Частичный сбой не приводит к потере результатов по успешным источникам.

---

## 3.2 Блок B — Нормализация и качество данных

### B1. Каноническая модель записи
Все источники приводятся к единой схеме сущности:
- имя/название;
- алиасы;
- тип сущности;
- идентификаторы;
- адреса;
- санкционные записи;
- источник и технические метаданные.

### B2. Валидация и карантин
- Невалидные записи не «роняют» пайплайн.
- Проблемные записи сохраняются в quarantine с причиной.

**Acceptance criteria:**
- Для каждой невалидной записи сохранена диагностика ошибки.
- Общее выполнение ETL завершается статусом `success | partial_failed | failed`.

---

## 3.3 Блок C — Хранилище и версияция

### C1. Доменное хранение
- Центральная БД PostgreSQL.
- Нормализованные сущности и связи (aliases, sanctions, identifiers, addresses).

### C2. Версионирование
- Снимок состояния записи при изменении.
- Возможность отследить, что изменилось между версиями.

### C3. Миграции
- Только миграционный путь изменений схемы.
- Обязательные backward-safe практики для production.

**Acceptance criteria:**
- Любое изменение схемы сопровождается миграцией.
- Возможен предсказуемый деплой на VPS без ручных SQL-правок.

---

## 3.4 Блок D — Поиск и матчинг

### D1. API поиска
Функции:
- поиск по строке запроса;
- ограничение количества результатов;
- настройка порога точности;
- фильтрация по источникам/программам/типу сущности.

### D2. Explainability
Каждый результат должен включать:
- итоговый `match_score`;
- причины совпадения (`match_reasons`);
- происхождение данных (источник, дата обновления).

### D3. Производительность поиска
- Индексация PostgreSQL (full-text + similarity).
- Подготовка к кэшированию частых запросов.

**Acceptance criteria:**
- Результат поиска возвращает объяснимый score.
- Время ответа остается стабильным при росте данных (контролируется метриками).

---

## 3.5 Блок E — Telegram Bot

### E1. Оповещения
Бот отправляет сообщения о:
- успешной загрузке данных;
- ошибке загрузки;
- падении API/health-check;
- аномалиях (слишком мало/слишком много изменений).

### E2. Операционные команды (этапно)
Минимальный набор:
- `/status` — состояние API и последних ETL запусков;
- `/run <source_code>` — ручной запуск источника;
- `/last_errors` — последние ошибки.

**Acceptance criteria:**
- Критические события доставляются в Telegram ≤ 1 минуты.
- Повторяющиеся ошибки дедуплицируются в заданном окне времени.

---

## 3.6 Блок F — Безопасность

### F1. HTTPS
- Публичный API доступен только по HTTPS.
- HTTP перенаправляется на HTTPS.

### F2. Изоляция БД
- БД не публикуется во внешний интернет.
- Доступ к БД только из внутренних сервисов.

### F3. Секреты и ключи
- Секреты хранятся вне репозитория.
- API ключи хранятся в hash-виде.
- Ротация ключей и токенов задокументирована.

### F4. Контроль доступа
- Разделение ролей/скоупов для search/import/admin.
- Ограничение rate limit для публичных endpoint.

**Acceptance criteria:**
- Невозможно подключиться к БД извне напрямую.
- Import API недоступен без валидного токена нужного scope.

---

## 3.7 Блок G — Наблюдаемость и надежность

### G1. Health checks
- `/health/live`
- `/health/ready`

### G2. Метрики
- длительность ETL;
- количество созданных/обновленных/ошибочных записей;
- latency API;
- error rates.

### G3. Логирование
- Structured logs (JSON).
- Correlation ID на запрос/задачу.

### G4. Ошибки и восстановление
- Централизованная обработка ошибок.
- Retry policy + DLQ/ошибочные очереди (по мере роста).

**Acceptance criteria:**
- Любой сбой ETL можно диагностировать по логам и метрикам.
- Сервис продолжает работать при локальных ошибках источников.

---

## 3.8 Блок H — Производительность и асинхронность

### H1. Async pipeline
- Асинхронная загрузка и обработка источников с ограничением параллелизма.

### H2. Кэширование
- Кэш популярных search-запросов.
- TTL и инвалидация по обновлению данных.

### H3. Оптимизация БД
- Индексы по полям поиска.
- Периодический аудит тяжелых запросов.

**Acceptance criteria:**
- Система демонстрирует улучшение p95 latency после включения кэширования.
- Медленный источник не блокирует обработку остальных.

## 4. Техническая архитектура (концептуально)

```text
[External Sanctions Sources]
            |
            v
    [Source Adapters (plugins)]
            |
            v
      [ETL Orchestrator]
            |
            v
 [Validation + Normalization Layer]
       |                    \
       |                     -> [Quarantine Storage]
       v
      [Import Domain Layer]
            |
            v
       [PostgreSQL DB] <----> [Cache]
            |
            v
         [Search API]
            |
            +-------> [Telegram Bot Interface]

[Monitoring + Alerts] observes ETL/API/DB and notifies Telegram
```

### 4.1 Рекомендованный стек (MVP на VPS)
- Backend/API: FastAPI
- Database: PostgreSQL
- Queue/Cache: Redis
- Migrations: Alembic
- Reverse proxy + TLS: Caddy/Nginx + Let's Encrypt
- Monitoring: Prometheus + Grafana + Alertmanager (или упрощенный стек на старте)
- Telegram integration: Bot API

### 4.2 Почему этот стек
- Минимальная операционная сложность для одного разработчика.
- Быстрое прототипирование и масштабирование по модулям.
- Большая экосистема инструментов и шаблонов для AI-assisted разработки.

## 6. API-контракты (высокоуровнево)

## 6.1 Search API
`GET /api/search`

Параметры:
- `q` (string, required)
- `limit` (int, default 20)
- `threshold` (float, default configurable)
- `sources[]` (optional)
- `entity_type` (optional)

Ответ:
- список сущностей с полями:
  - `entity`
  - `sanctions[]`
  - `match_score`
  - `match_reasons[]`

## 6.2 Internal import API
`POST /internal/import/bulk`

- Доступ только с service key / internal network.
- Поддержка batch-импорта с детальным итогом.

## 6.3 Ops API (минимум)
- `GET /health/live`
- `GET /health/ready`
- `GET /metrics`

## 7. Требования к безопасности

1. Внешний трафик только HTTPS.
2. БД недоступна из внешней сети.
3. Секреты не хранятся в коде и Docker-образах.
4. Для ключей/токенов действует ротация и срок жизни.
5. Ограничение частоты запросов и лимит payload size.
6. Логи действий администрирования и импорта обязательны.
7. Регулярная проверка зависимостей на уязвимости.

---

## 8. Нефункциональные требования

### 8.1 Надежность
- ETL устойчив к сбоям отдельных источников.
- API и ETL мониторятся автоматически.

### 8.2 Производительность
- Поиск оптимизирован индексами и кэшем.
- Поддерживается деградация без падения сервиса при перегрузке.

### 8.3 Поддерживаемость
- Четкая модульная структура.
- Минимум дублирования логики.
- Все изменения схемы через миграции.

### 8.4 Расширяемость
- Источники добавляются независимо.
- Дальнейшая декомпозиция в микросервисы выполняется постепенно, по факту роста нагрузки.

## 9. План разработки (roadmap)

## Phase 1 — Foundation (MVP)
- Каркас проекта.
- Базовая БД и миграции.
- Реестр источников.
- 1-2 источника через унифицированный интерфейс.
- Search API + базовый scoring.
- Telegram уведомления об ETL/API событиях.
- HTTPS и изоляция БД на VPS.

**Результат:** рабочая система с безопасным базовым контуром и мониторингом.

## Phase 2 — Stability & Performance
- Асинхронная обработка источников.
- Кэширование search-запросов.
- Улучшенная обработка ошибок и ретраи.
- Расширенные метрики/дашборды.

**Результат:** стабильная ежедневная эксплуатация при росте данных.

## Phase 3 — Source scaling
- Подключение новых источников независимыми циклами.
- Контрактные тесты для каждого нового адаптера.
- Улучшение дедупликации и explainability.

**Результат:** масштабируемое расширение покрытия санкционных списков.

## Phase 4 — Advanced matching & microservice readiness
- Подготовка ML-пайплайна для reranking.
- Выделение сервисных границ (ingestion/search/notification) при необходимости.

**Результат:** готовность к дальнейшему росту без архитектурного тупика.

## 10. Риски и меры

1. **Частые изменения форматов источников**  
   Мера: контрактные тесты + fallback обработка + алерты.

2. **Ложные совпадения или пропуски в поиске**  
   Мера: explainability, порог точности, эволюция алгоритма матчинга.

3. **Операционные сбои на VPS**  
   Мера: health checks, Telegram-алерты, backup/restore runbook.

4. **Рост сложности при добавлении источников**  
   Мера: жесткий plugin-контракт и шаблон адаптера.

5. **Уязвимости безопасности**  
   Мера: hardening checklist + dependency scanning.

## 13. Критерии приемки продукта (release-level)

Релиз считается успешным, если:
1. API-поиск стабильно работает и возвращает объяснимые результаты.
2. Источники подключаются как независимые адаптеры через единый интерфейс.
3. ETL процессы наблюдаемы, с ошибками и результатами в Telegram.
4. Базовые требования безопасности соблюдены (HTTPS, закрытая БД, scoped keys).
5. Схема БД эволюционирует только через миграции.
6. Система развернута и поддерживается на VPS без ручной «магии».
